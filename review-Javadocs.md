# Review: Javadocs

## Summary
The documentation is incomplete at the method level, especially in older GameTests and the new shared service APIs. Some recently added test descriptions claim to reproduce behavior that their tests do not exercise, and a few production comments still describe an earlier architecture. The first priority is to give each player-visible test a usable setup, action, and expected result, then document the lifecycle and mutation contracts introduced by the shared architecture.

### 2. The nested-batch test claims to exercise a collapse that never happens
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/gametest/java/com/github/crittscott/somestacks/gametest/StackFoundationChecks.java:62; forge/src/gametest/java/com/github/crittscott/somestacks/gametest/CapabilityAndPersistenceGameTests.java:123; fabric/src/gametest/java/com/github/crittscott/somestacks/gametest/CapabilityAndPersistenceGameTests.java:120
- **In plain English:** The instructions say this test includes removing a Bar that causes other Bars to fall. The test only adds items while opening and closing internal update groups; it never removes a Bar or makes one fall.
- **Consequence:** The owner can incorrectly treat a passing test as evidence that nested Bar collapse is covered, and someone following the instructions performs a different scenario from the automated test.
- **Action:** Rewrite the shared description to say that this is an internal publication-order test with no direct manual reproduction, and describe only its existing insertions and light assertions. Replace the loader summaries with Javadoc links to the shared method. Put any manual Bar collapse procedure with the actual collapse tests rather than claiming it here.
- **Technical detail:** `nestedBatchesPublishOnlyAfterTheOuterBatch` calls `checkNestedBatch` for all three block types. That helper invokes `beginBatch` twice through reflection, writes slots 0 and 1, invokes `publishIfPending`, and closes the batches. There is no call to extraction or collapse. Only Storage and Singles assert derived light; the Bar fixture is an ordinary accepted Bar item.

### 3. Shared lifecycle and mutation entry points omit their calling contracts
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/ServerLifecycle.java:17,25,32,36; common/src/main/java/com/github/crittscott/somestacks/client/ClientGestures.java:19,30; common/src/main/java/com/github/crittscott/somestacks/client/ClientRenderPacketSink.java:34,39,52,58; common/src/main/java/com/github/crittscott/somestacks/util/StackItemStorage.java:29,45,141,157; common/src/main/java/com/github/crittscott/somestacks/block/RunEdit.java:36,40; common/src/main/java/com/github/crittscott/somestacks/client/ItemRenderOverrides.java:123,129,135
- **In plain English:** The new shared interfaces do more than their names reveal, but their method documentation does not explain those effects. For example, loading inventory bypasses change notifications, and receiving appearance messages before rendering is installed preserves only some messages.
- **Consequence:** A maintainer implementing or changing a loader adapter must inspect method bodies to learn initialization order, whether contents are copied, whether changes publish automatically, and which messages can be lost before setup. Mistakes at those boundaries can leave stale item shapes or appearance state without any indication in the API documentation.
- **Action:** Add method contracts at these entry points. Document server start/stop cleanup and per-world policy loading; sender installation's returned previous sender and sync reset; disabled-mode skipping; rendering-handler installation and each packet overload's preinstallation behavior; fixed inventory capacity, direct stack ownership, notification bypass on NBT loading, and the caller's derived-state refresh responsibility; server-thread use and balanced `RunEdit.begin/end`; and override replacement/removal plus cache invalidation.
- **Technical detail:** These are custom public methods with no method Javadoc, not inherited vanilla or loader methods. `StackItemStorage.setStackInSlot` stores the supplied object and calls `onContentsChanged`, whereas `deserializeNBT` clears/replaces storage without calling that hook. `ClientRenderPacketSink.apply(ConfigSyncPkt)` retains overrides even without a handler, but its other two overloads do not retain packets. `ClientGestures.setSender` resets synchronization; `cycleMode` skips disabled block types. `RunEdit.end` releases a global flag whose callers use a `finally` block. The three override mutations invalidate resolved profiles. The class summaries do not state these caller obligations.

### 4. Two production Javadocs still describe superseded assumptions
- **Severity:** Low
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/block/StorageStackBE.java:23; common/src/main/java/com/github/crittscott/somestacks/command/SsCommand.java:209
- **In plain English:** The storage description sends a reader toward a block's local contents as the automation interface, although automation actually addresses the whole pile. The deny-command description says shipped defaults name absent mods, but the current defaults are empty.
- **Consequence:** A maintainer following the storage description can investigate or adapt the wrong inventory boundary. Someone changing configuration validation can preserve an obsolete assumption about the default deny list rather than the actual reason an administrator may name an unloaded mod.
- **Action:** Describe loader automation as an adapter over `StackBlockEntity.itemRun()` and distinguish it from `getItems()` local storage. Rewrite the deny-subtree description to say namespace entries can intentionally name unloaded mods, without claiming the defaults do so.
- **Technical detail:** `RunItemHandlerBase` resolves `blockEntity.itemRun()` for whole-run reads and mutations; `FabricRunItemStorage` does the same and shares the bottom block's transaction ledger. `getItems()` is local storage, used directly only for relevant local access/fallback. `ServerConfig.Settings.defaults` supplies `List.of()` for both disabled namespace and disabled item lists, contradicting the stated shipped-default rationale in `SsCommand`.

These passages are implementation/design commentary rather than caller-facing documentation of the existing operation.

## Drift from the expected way
The documentation mostly uses conventional Javadoc syntax, but it has not followed the architecture migration at method boundaries: new shared APIs lack contracts (finding 3), two descriptions still point to prior assumptions (finding 4), and older tests remain undocumented as manual procedures (finding 1). Several run-operation comments substitute implementation narratives and hypothetical designs for concise contracts (finding 5), while the nested-batch description overstates what its test proves (finding 2).
