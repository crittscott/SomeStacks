# Review: Organization

## Summary
The main remaining fragmentation is in gesture recognition and column movement. Client click handling uses a class for almost every condition, while Singles gravity and Bar collapse still live outside the classes that own their runs. Consolidate those behaviors into their existing owners; player gesture state also has a smaller opportunity to unify its storage and cleanup.

## Findings

### 1. Client gesture recognition is spread across an unnecessary rule framework
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/client/ClientGestures.java:11; common/src/main/java/com/github/crittscott/somestacks/client/interaction/InteractionRule.java:11; common/src/main/java/com/github/crittscott/somestacks/client/interaction/InteractionRuleRegistry.java:14; common/src/main/java/com/github/crittscott/somestacks/client/interaction/InteractionContext.java:20; common/src/main/java/com/github/crittscott/somestacks/client/interaction/ModeCycleRule.java:10; common/src/main/java/com/github/crittscott/somestacks/client/interaction/TogglePermanentRule.java:9; common/src/main/java/com/github/crittscott/somestacks/client/interaction/RotateBlockWithRedstoneTorchRule.java:9; common/src/main/java/com/github/crittscott/somestacks/client/interaction/RotateItemWithSoulTorchRule.java:9; common/src/main/java/com/github/crittscott/somestacks/client/interaction/DepositIntoClickedStackRule.java:17; common/src/main/java/com/github/crittscott/somestacks/client/interaction/DepositIntoAdjacentStackRule.java:11; common/src/main/java/com/github/crittscott/somestacks/client/interaction/PlaceAdjacentGenericRule.java:9; common/src/main/java/com/github/crittscott/somestacks/client/interaction/ExtractionRule.java:9; forge/src/main/java/com/github/crittscott/somestacks/client/ClientEvents.java:63; fabric/src/main/java/com/github/crittscott/somestacks/client/FabricClientEvents.java:51; fabric/src/main/java/com/github/crittscott/somestacks/mixin/MinecraftMixin.java:35; common/src/gametest/java/com/github/crittscott/somestacks/gametest/ClientGestureChecks.java:46.
- **In plain English:** Deciding whether a right-click belongs to the mod takes eleven separate files, even though every block-click choice has the same result: consume the click locally and let the server do the work. The order deciding which gesture wins lives separately from the gesture conditions.
- **Consequence:** A maintainer changing overlapping gestures must open the registry, individual condition classes, the mutable click context, and tests that name those classes to understand one decision. Even a behavior-preserving consolidation requires rewriting tests because they treat the implementation class as the gesture's identity.
- **Action:** Move air-click handling and ordered block-click recognition into ClientGestures, using ordinary methods and a nested gesture enum if tests need to distinguish decisions. Return the consumption decision directly, update loader callbacks and the Fabric air-click mixin to call it, update ClientGestureChecks to assert gesture values and consumption, and delete the interaction rule framework. Keep the existing condition order and top-face deposit checks.
- **Technical detail:** InteractionRuleRegistry has two identical one-element air-click lists and a fixed seven-element block list; there is no registration or extension mechanism. Every block rule's execute method only calls InteractionContext.cancelEvent(). InteractionContext is a mutable input/output carrier with factories and numerous convenience getters, while ClientGestures already owns selection, messaging, and synchronization. The only production consumers of registry results read shouldCancel(); concrete winner classes matter only to GameTests. These pieces form one coherent client gesture responsibility without requiring an interface, object dispatch, or separate files per condition.

### 2. Column movement still lives partly in individual block entities
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBE.java:169; common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBE.java:224; common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBE.java:246; common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBE.java:305; common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBE.java:321; common/src/main/java/com/github/crittscott/somestacks/block/SinglesColumn.java:233; common/src/main/java/com/github/crittscott/somestacks/block/BarStackBE.java:143; common/src/main/java/com/github/crittscott/somestacks/block/BarStackBE.java:201; common/src/main/java/com/github/crittscott/somestacks/block/BarStackBE.java:257; common/src/main/java/com/github/crittscott/somestacks/block/BarColumn.java:255; common/src/main/java/com/github/crittscott/somestacks/block/BarStackBlock.java:184; common/src/main/java/com/github/crittscott/somestacks/server/StackInteractions.java:306; common/src/main/java/com/github/crittscott/somestacks/server/StackInteractions.java:324.
- **In plain English:** The classes describing an entire column handle machine operations, but much of the movement through that column is implemented inside a class describing just one block. Singles items falling through several blocks and Bar collapses therefore have a different home from column insertion and machine extraction.
- **Consequence:** A maintainer changing movement, empty-block cleanup, or publication must trace between block entities, run classes, and block removal callbacks to find the whole operation. Bar cleanup in particular has two owners: player collapse removes blocks in BarStackBE, while machine extraction trims them in BarColumn. This creates extra places to update when the shared removal rules change.
- **Action:** Make SinglesColumn own extraction, gravity across rotated seams, and empty-block cleanup for both players and automation. Make BarColumn own player extraction/collapse as a distinct method alongside its existing automation backfill, including the static entry point for collapse after a block is removed. Route StackInteractions and BarStackBlock directly to these run operations, remove the displaced block-entity entry points, and keep block entities responsible for local inventory, rotations, shapes, and the local cascade-removal flag. Preserve the existing player-versus-automation Bar behavior and WorldEdits permission checks.
- **Technical detail:** SinglesColumn.extract ultimately calls SinglesStackBE.extractAt, whose drawDownColumn walks other block entities, transfers items and rotations, publishes edits, and removes empty blocks through WorldEdits. BarStackBE.cascadeFrom likewise walks upward, batches multiple entities, removes blocks, and collects drops; BarStackBlock.onRemove enters that walk through BarStackBE.collapseAbove. BarColumn separately implements run-wide backfill and trimEmptyTop. These are concrete run algorithms, so placing them in the existing concrete run classes makes ownership consistent without introducing another helper class or combining the genuinely different movement models. The removal entry point must resolve the surviving column above the removed position, rather than depend on a run instance containing the block already removed.

### 3. One player's gesture session is stored and cleared in separate owners
- **Severity:** Low
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/server/ServerGestureState.java:13; common/src/main/java/com/github/crittscott/somestacks/server/GestureThrottle.java:25; common/src/main/java/com/github/crittscott/somestacks/server/GestureThrottle.java:28; common/src/main/java/com/github/crittscott/somestacks/ServerLifecycle.java:17; common/src/main/java/com/github/crittscott/somestacks/ServerLifecycle.java:25; common/src/main/java/com/github/crittscott/somestacks/ServerLifecycle.java:36; common/src/main/java/com/github/crittscott/somestacks/server/StackInteractions.java:52; common/src/main/java/com/github/crittscott/somestacks/server/StackSounds.java:27.
- **In plain English:** The server remembers a player's selected gesture mode and their recent clicks in separate places. Login-session cleanup has to remember to clear both places each time.
- **Consequence:** Maintainers implementing session resets or adding per-player gesture state must maintain coordinated cleanup calls in server start, server stop, logout, and test setup. The current cleanup is complete, but its completeness depends on callers knowing about both owners rather than asking one owner to forget a player's gesture session.
- **Action:** Fold gesture and rotation-sound pacing into ServerGestureState, using one private per-player entry holding mode, modifier, and optional last-attempt/sound ticks. Provide claimTick and claimRotationSound there, update callers, and delete GestureThrottle. Keep clear and clearAll as the single session cleanup operations, preserving the default mode and first-attempt behavior.
- **Technical detail:** ServerGestureState holds one UUID-keyed map; GestureThrottle holds two more with the same player/session lifetime. ServerLifecycle.starting, stopped, and logout explicitly pair their clearing calls. No loader difference or independent lifetime requires the split. Consolidation removes that coordination requirement without mixing server gesture state with unrelated configuration or gallery state.

## Drift from the expected way
The principal departure is the home-grown client rule dispatch in finding 1, which adds an object framework around native loader click callbacks whose shared job is a simple decision. Findings 2 and 3 are ownership drift within the mod rather than missing vanilla or loader facilities: existing run and gesture-session owners can absorb the scattered behavior without new abstractions.
