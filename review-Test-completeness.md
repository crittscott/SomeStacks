# Review: Test-completeness

## Summary
The suite covers much of the mod's inventory behavior, cross-block movement, loader storage integration, and native interaction/protection paths. It is incomplete at a few distinct boundaries: rejecting server packets without side effects, breaking a run into two surviving runs, and executing administrative commands with the correct permissions. Add focused tests for those boundaries; the existing finite geometry checks and shared scenarios do not justify trimming the suite as over-complete.

## Findings

### 1. Server packet rejection has no tests for its actual side effects
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/test/java/com/github/crittscott/somestacks/network/PacketCodecTest.java:47; common/src/main/java/com/github/crittscott/somestacks/network/ConfigSyncPkt.java:76; common/src/main/java/com/github/crittscott/somestacks/network/ConfigSyncPkt.java:90; common/src/main/java/com/github/crittscott/somestacks/network/WriteOverridesPkt.java:48; common/src/main/java/com/github/crittscott/somestacks/client/ClientRenderPacketSink.java:39; common/src/main/java/com/github/crittscott/somestacks/client/ClientRenderPacketSink.java:58
- **In plain English:** The tests check that ordinary server messages can be read back, but do not check that rejected messages leave the player's settings and files alone. An invalid message must not be mistaken for an ordinary empty message, which intentionally clears settings or requests a file write.
- **Consequence:** Maintainers can change the packet readers or client dispatch and accidentally turn refusal into clearing server overrides, changing enabled stack types, or requesting a local file write without any current test failing.
- **Action:** Extend PacketCodecTest with negative and above-limit counts for both packet types, then apply the decoded packets through ClientRenderPacketSink using a recording Handler. Seed valid override and enablement state, assert that rejected config packets preserve it and invoke no handler, and assert that rejected write packets invoke no write. Include valid empty packets as the contrasting accepted cases, and one invalid numeric render field traveling through ConfigSyncPkt.decode to verify sanitization at this boundary. Restore static sink/client state after each test.
- **Technical detail:** ConfigSyncPkt uses a null override map as its rejection sentinel because an empty map is meaningful; WriteOverridesPkt uses a null list because an empty list means writing the user layer. Their receiving branches are absent from the tests: PacketCodecTest exercises valid optional fields and writes, while OverrideJsonCodecTest tests numeric sanitization directly rather than via the wire decoder. A recording sink tests the complete refusal path without touching disk or needing a running client.

### 2. Removing a middle Storage or Singles block is untested
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/block/StorageStackBlock.java:148; common/src/main/java/com/github/crittscott/somestacks/block/SinglesStackBlock.java:167; common/src/gametest/java/com/github/crittscott/somestacks/gametest/StackFoundationChecks.java:113; common/src/gametest/java/com/github/crittscott/somestacks/gametest/StoragePileChecks.java:97; common/src/gametest/java/com/github/crittscott/somestacks/gametest/SinglesColumnChecks.java:286
- **In plain English:** Breaking a block in the middle of a tall stack leaves separate stacks above and below it. The current Storage and Singles tests remove a top block or extract an item, so they never check both surviving stacks after a middle block breaks.
- **Consequence:** A regression in either side's scheduled updates, inventory separation, or local drops can survive the suite. Players would notice missing or duplicated contents, a Storage half that no longer packs itself, or outdated light/comparator output after breaking a middle block.
- **Action:** Add one shared GameTest per type, registered in both loaders' existing holders. Create at least three occupied blocks, prime both ends' cached run views, make a pending edit in the upper block, then replace the middle block with air through the world block-change path. Assert exact drops from the removed block only; after scheduled ticks, assert distinct upper/lower run bounds, total item conservation, independent comparator/light publication, Storage packing within each half, and Singles contents/rotations staying in the upper half.
- **Technical detail:** Both onRemove implementations explicitly invalidate the former run and mark positions above and below dirty. The upper run acquires a new base, so the previously scheduled tick at the old base cannot publish or settle it. StackFoundationChecks.checkBounds removes only the top of a two-block run and checks immediate bounds; SinglesColumnChecks.comparatorFollowsAColumnLosingABlock also removes the top. Storage extraction scheduling exercises an intact pile. Bar removal/collapse coverage does not exercise these different Storage/Singles removal paths.

### 3. Administrative command tests inspect registration but never execute permissions
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/test/java/com/github/crittscott/somestacks/command/CommandRegistrationTest.java:19; common/src/main/java/com/github/crittscott/somestacks/command/SsCommand.java:132; common/src/main/java/com/github/crittscott/somestacks/command/SsCommand.java:217; common/src/main/java/com/github/crittscott/somestacks/command/SsCommand.java:664; common/src/gametest/java/com/github/crittscott/somestacks/gametest/RenderGalleryChecks.java:25; common/src/gametest/java/com/github/crittscott/somestacks/gametest/ServiceAndConfigChecks.java:40
- **In plain English:** Tests confirm that command names exist, but never check whether an ordinary player is refused or an authorized administrator can use them. The gallery test directly starts construction, bypassing the command that keeps this world-replacing tool disabled by default.
- **Consequence:** Removing a permission requirement or wiring a command to the wrong policy list would not fail the current tests. Maintainers would have no regression check for who may start a gallery, whether its disabled setting is enforced, or whether a deny command actually changes the intended admission rule.
- **Action:** Add shared GameTests that execute the registered dispatcher with player command sources: deny an ordinary player a policy edit and gallery; deny an administrator a gallery while disabled; deny a below-threshold administrator when enabled; allow a player at the configured threshold. Add one authorized `/ss deny item add minecraft:stone`/remove cycle and one unknown-item refusal, asserting policy/admission changes and unchanged state on refusal. Isolate and restore policy and player permission state, and register the scenarios in both loader holders.
- **Technical detail:** CommandRegistrationTest checks child nodes, endpoint presence, numeric argument ranges, and translation keys; it never calls dispatcher.execute or evaluates source requirements. RenderGalleryChecks calls RenderGalleryGenerator.enqueue directly, and ServiceAndConfigChecks calls ServerConfig.addListEntry directly. Neither verifies SsCommand.galleryTree's player/config/permission predicate or addItemEntry's registry validation and actual list binding. These are separate command-boundary checks, rather than repeats of the existing builder or immutable-policy tests.

## Drift from the expected way
The tests use JUnit and loader GameTests in conventional roles; no home-grown test framework needs replacement. The gaps are in carrying meaningful scenarios through the production boundary: client dispatch in finding 1, world removal and scheduled ticks in finding 2, and Brigadier execution in finding 3.
