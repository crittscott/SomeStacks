# Review: Expected-way

## Summary
The remaining departures from standard loader and vanilla facilities are concentrated in automation actors, Forge configuration, and placement obstruction checks. Replace the manually constructed Fabric automation player first: the project already uses Fabric's supported fake-player facility in its tests. Forge policy persistence and the shared obstruction scan also duplicate facilities available on their respective platforms.

## Findings

### 1. Fabric creates its own automation player
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** fabric/src/main/java/com/github/crittscott/somestacks/server/FabricEditAuthority.java:31, fabric/src/main/java/com/github/crittscott/somestacks/server/FabricEditAuthority.java:35, fabric/src/main/java/com/github/crittscott/somestacks/server/FabricEditAuthority.java:38; fabric/src/gametest/java/com/github/crittscott/somestacks/gametest/ProtectionGameTests.java:46
- **In plain English:** Machines are represented by a made-up player when they grow or remove stacks. Fabric already supplies a player specifically designed for this purpose, but the live mod constructs an ordinary server player instead, while the tests use Fabric's supplied player.
- **Consequence:** Maintainers must manage an extra cache of artificial players and reason about an ordinary player's suitability for machine actions. The test setup also exercises a different kind of player from the production automation actor, so those tests do not establish that the live actor behaves like Fabric's supported automation player.
- **Action:** Implement `automationActor` using `net.fabricmc.fabric.api.entity.FakePlayer.get(level)`, already used by this project's Fabric GameTests. Delete the manual `ServerPlayer` construction, profile generation, and `actors` map. Update the class description to describe the native Fabric actor.
- **Technical detail:** `FabricEditAuthority.automationActor` currently caches `new ServerPlayer(key.getServer(), key, PROFILE)` in a `WeakHashMap`. `WorldEdits` uses this actor for spawn protection, growth, and removal, and `FabricEditAuthority.vetoesRemoval` passes it to `PlayerBlockBreakEvents.BEFORE`. In contrast, `ProtectionGameTests` imports Fabric API's `FakePlayer` and obtains its actor with `FakePlayer.get(helper.getLevel())`. The available loader facility is demonstrated directly by repository code; no fabricated player/cache implementation is necessary.

### 2. Forge policy bypasses Forge's server configuration system
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** forge/src/main/java/com/github/crittscott/somestacks/SomeStacks.java:50, forge/src/main/java/com/github/crittscott/somestacks/SomeStacks.java:66; common/src/main/java/com/github/crittscott/somestacks/ServerLifecycle.java:21; common/src/main/java/com/github/crittscott/somestacks/ServerConfig.java:180, common/src/main/java/com/github/crittscott/somestacks/ServerConfig.java:188, common/src/main/java/com/github/crittscott/somestacks/ServerConfig.java:222
- **In plain English:** Forge server settings use a custom JSON file that the mod reads and writes itself. Forge already provides a world-specific server-settings system, but Some Stacks does not register with it.
- **Consequence:** Server admins get a separate configuration format and restart-only file loading rather than the usual Forge server-config workflow. Maintainers own file creation, parsing, validation, saving, and world-session loading that Forge already provides, and changes to the common reader must be evaluated for both loaders even though Forge has its own facility.
- **Action:** Register a Forge `ForgeConfigSpec` as `ModConfig.Type.SERVER` through `ModLoadingContext`. Populate the existing common immutable `ServerConfig.Settings` from Forge config loading/reloading events, and save command edits through the registered config values. Keep Fabric's JSON persistence behind the loader boundary, where it is needed; keep policy interpretation and immutable settings common. If the immediately preceding released version used the JSON policy file, convert its saved settings once through the dedicated migration layer and thereafter write only the current Forge format.
- **Technical detail:** Forge startup delegates to `ServerLifecycle.starting`, which unconditionally resolves `<world>/serverconfig/somestacks-server.json` and calls the common JSON loader. `ServerConfig.Persistence` implements the entire persistence boundary, including defaults and numeric clamping. The Forge entrypoint registers no native config, and its startup-method Javadoc explicitly calls the implementation a hand-rolled reader/writer without automatic file-watch reload. Fabric's lack of a matching built-in config system is a loader-specific reason to retain that implementation there, not a reason to bypass Forge's server config facility.

### 3. Placement obstruction duplicates the vanilla shape check
- **Severity:** Medium
- **Confidence:** Likely
- **Where:** common/src/main/java/com/github/crittscott/somestacks/server/WorldEdits.java:83, common/src/main/java/com/github/crittscott/somestacks/server/WorldEdits.java:88; common/src/main/java/com/github/crittscott/somestacks/block/StoragePile.java:310; common/src/main/java/com/github/crittscott/somestacks/block/SinglesColumn.java:201; common/src/main/java/com/github/crittscott/somestacks/block/BarColumn.java:220
- **In plain English:** Before a stack grows, the mod searches nearby creatures and players and calculates whether they overlap its completed shape. Minecraft already has a shape-based check for whether entities obstruct placement.
- **Consequence:** Maintainers must keep the mod's entity filtering and shape-overlap rules consistent with Minecraft's placement rules for all three stack types. A future change to one rule requires separately updating this hand-written copy instead of automatically using the vanilla check.
- **Action:** Retain the block-local to world-space shape conversion, then delegate to the vanilla entity-and-shape `isUnobstructed` facility on the level, using a null excluded entity to retain the current policy of checking every obstruction. Keep passing the final occupied shape for Singles and Bar; replacing it with the empty block's collision shape would lose the existing placement requirement.
- **Technical detail:** `WorldEdits.isUnobstructed` moves the shape to world coordinates, calls `level.getEntities`, filters removed entities and `blocksBuilding`, creates a shape for each bounding box, and computes `Shapes.joinIsNotEmpty(..., BooleanOp.AND)`. This is the work the vanilla `isUnobstructed(Entity, VoxelShape)` facility performs. The same custom check feeds both player placement through `placeChecked` and the growth-feasibility checks in all three run classes. Confidence is Likely because the exact mapped native overload has not been independently checked against published API material, as required by this review's no-research rule.

## Drift from the expected way
The drift is concentrated rather than spread throughout loader integration: Fabric substitutes a custom actor for its native fake player (finding 1), Forge shares a custom configuration implementation despite having a server-config facility (finding 2), and all three stack types share a home-grown obstruction check (finding 3). These are places to use the established platform mechanism while retaining common gameplay policy.
