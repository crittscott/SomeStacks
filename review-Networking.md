# Review: Networking

## Summary
The main trust-boundary gap is that a server can change and save the client's personal render settings without a locally initiated request. Gesture execution is paced, but the separate state packet bypasses that pacing and queues work for every message. Invalid synchronized render entries also produce a warning for every bad field, allowing a server to turn small packets into substantial client log traffic.

## Findings

### 1. A server can overwrite personal client settings and trigger file generation
- **Severity:** High
- **Confidence:** Certain
- **Where:** forge/src/main/java/com/github/crittscott/somestacks/network/ForgePacketHandlers.java:41, forge/src/main/java/com/github/crittscott/somestacks/network/ForgePacketHandlers.java:56, fabric/src/main/java/com/github/crittscott/somestacks/network/FabricClientNetworking.java:27, common/src/main/java/com/github/crittscott/somestacks/client/ClientRenderPacketSink.java:52, common/src/main/java/com/github/crittscott/somestacks/client/ClientRenderPacketSink.java:58, common/src/main/java/com/github/crittscott/somestacks/client/DefaultClientRenderPacketHandler.java:19, common/src/main/java/com/github/crittscott/somestacks/client/DefaultClientRenderPacketHandler.java:30, common/src/main/java/com/github/crittscott/somestacks/client/ItemRenderOverrides.java:129, common/src/main/java/com/github/crittscott/somestacks/client/ItemRenderOverrides.java:135, common/src/main/java/com/github/crittscott/somestacks/client/ItemRenderOverrides.java:188, common/src/main/java/com/github/crittscott/somestacks/client/ItemRenderOverrides.java:217
- **In plain English:** Joining a server gives it the ability to change your personal item appearance settings and save those changes on your computer. It can also order your client to generate files and inspect every item's appearance, even though you never typed a write command.
- **Consequence:** A malicious server can reset existing personal overrides, replace them with its own settings, and send a write request to persist the damage across later sessions and other servers. Repeated generation requests perform model measurement, registry traversal, serialization, and disk writes on the client thread, freezing the player's game.
- **Action:** Move personal override editing and writing to locally registered client commands on both loaders. Keep server-imposed appearance in the existing session-scoped ConfigSyncPkt layer; remove unsolicited server authority over the personal override map and file-generation operations. If server command responses must remain, accept them only against an explicit pending local request with the requested operation and arguments, consume that request once, and clear it on disconnect.
- **Technical detail:** RenderOverridePkt directly calls putUser/removeUser, and WriteOverridesPkt directly calls handleWriteRequest/handleDumpRequest. None of the receivers checks for local intent. An attacker can send resets for known item ids followed by an empty namespace list to write the altered USER_OVERRIDES map to item_overrides.json. Namespace validation and path containment prevent path traversal but do not authorize the operation or limit repeated work; a nonempty request traverses the registry and writes one file per accepted namespace.

### 2. State packet floods bypass the gesture throttle
- **Severity:** High
- **Confidence:** Likely
- **Where:** common/src/main/java/com/github/crittscott/somestacks/network/GestureStatePkt.java:22, common/src/main/java/com/github/crittscott/somestacks/server/ServerGestureState.java:21, forge/src/main/java/com/github/crittscott/somestacks/network/ForgePacketHandlers.java:21, forge/src/main/java/com/github/crittscott/somestacks/network/ForgePacketHandlers.java:73, fabric/src/main/java/com/github/crittscott/somestacks/network/FabricNetworking.java:53, common/src/main/java/com/github/crittscott/somestacks/server/GestureThrottle.java:35
- **In plain English:** The limit on stack clicks does not limit the messages announcing which stack mode a player selected. A modified client can keep sending these messages and make the server process every one, including identical repeats.
- **Consequence:** A malicious client can fill the server's work queue with state updates, causing allocation and main-thread work without performing any stack gesture. Actual lag depends on the connection's incoming rate and the server's broader packet limits, but this mod supplies no bound at either transport entry point.
- **Action:** Add a connection-scoped ingress rate limit before scheduling state-packet work on each loader, with a small burst allowance for normal mode changes and clicks; disconnect clients that exceed it. Preserve the ordering of accepted state updates before ordinary block-use packets, and release limiter state on disconnect. Also avoid allocating a replacement State when the accepted mode and modifier match the stored values.
- **Technical detail:** Every accepted custom payload reaches ctx.enqueueWork or server.execute before any mod-specific limit is checked. GestureStatePkt.handleServer unconditionally updates a HashMap with a newly allocated State. GestureThrottle.claimTick is called only later in StackInteractions.handleBlockClick, so it never applies to a stream consisting solely of GestureStatePkt messages. Merely throttling handleServer would leave the queue-allocation exposure in place.

### 3. Invalid render fields amplify incoming packets into log traffic
- **Severity:** Medium
- **Confidence:** Certain
- **Where:** common/src/main/java/com/github/crittscott/somestacks/network/ConfigSyncPkt.java:23, common/src/main/java/com/github/crittscott/somestacks/network/ConfigSyncPkt.java:82, common/src/main/java/com/github/crittscott/somestacks/renderconfig/OverrideJsonCodec.java:48, forge/src/main/java/com/github/crittscott/somestacks/network/ForgePacketHandlers.java:50, common/src/main/java/com/github/crittscott/somestacks/client/DefaultClientRenderPacketHandler.java:25
- **In plain English:** Bad item appearance numbers are rejected, but each bad number causes a separate log warning. A server can repeatedly send many bad values and make your client write large amounts of diagnostic text.
- **Consequence:** Players connecting to a malicious server get avoidable client disk activity and expanding log files. A single config message can produce warnings for both the scale and offset of every entry, including repeated item ids that eventually collapse to one stored override.
- **Action:** Make the shared numeric sanitizer silent for network use and collect validation failures at the packet boundary. Emit at most one bounded summary per rejected message, rate-limit those summaries per connection, and reject duplicate item ids rather than repeatedly sanitizing them. Apply the same logging limit to individual RenderOverridePkt messages.
- **Technical detail:** ConfigSyncPkt accepts up to MAX_OVERRIDE_ENTRIES and invokes OverrideJsonCodec.sanitize for every encoded entry before inserting it into a map. sanitize logs independently for invalid scale and offset, so NaN scales and invalid offsets cause two warnings per entry; no uniqueness check or warning budget intervenes. Repeated RenderOverridePkt packets reach the same logging path on the client thread.

## Drift from the expected way
The most significant drift is executing client-local edits and file writes as unsolicited server instructions instead of locally authorized client operations (finding 1). The loader transports are native, but their state receivers lack an ingress work budget (finding 2), and network validation uses file-parser-style per-field warning output instead of bounded connection diagnostics (finding 3).
